## 🏠 进程隔离：每个 App 住自己的房子

Linux/Android 上**每个进程有自己独立的虚拟内存空间**：

```
微信进程：0x0000~0xFFFF 看到的是自己的代码 + 数据
B站进程：0x0000~0xFFFF 看到的是自己的代码 + 数据

它们互相看不到对方的内存（除非用 IPC）
```

**结果**：你想改微信的行为，**必须让代码跑在微信的进程里**。从外面（比如你的模块进程）没法直接改微信内存。

## 🚪 怎么"进"别人进程

主流方法有 4 种：

### 方法 1：Zygisk（最优雅）

利用"所有 App 都是 Zygote fork 的"这一点，在 **Zygote 阶段**就把代码注进去：

```
Zygote 进程
   ↓ fork
新进程（带着 Zygisk 代码）
   ↓
新进程 exec 微信的代码
   ↓
变成"微信进程"，但里面已经有 Zygisk + LSPosed 了
```

**优点**：每个 App 出生时自带，不需要"入侵"动作  
**缺点**：只能 hook Java 层（ART hook），hook 不了 init 这种系统进程

### 方法 2：ptrace 注入（Frida 用的）

用 Linux 的 `ptrace` 系统调用附加到目标进程：

```
你的进程                微信进程
   │                       │
   │ ptrace(ATTACH, 微信pid)│
   ├──────────────────────>│  ← 微信被暂停
   │                       │
   │ 在微信内存里写入 .so 路径
   │ 修改微信的某条指令跳到 dlopen
   ├──────────────────────>│  ← 微信跑起来，加载你的 .so
   │                       │
   │ ptrace(DETACH)        │
   ├──────────────────────>│  ← 你撤了，但 .so 已经在微信里跑
```

**优点**：能 hook native（C/C++）  
**缺点**：要 root，会被反调试检测

### 方法 3：LD_PRELOAD

设置环境变量，让动态链接器在加载程序时先加载你的库：

```bash
LD_PRELOAD=/path/to/mylib.so /system/bin/app_process ...
```

**优点**：简单  
**缺点**：得能控制 App 的启动命令，对普通 App 没用（你改不了 AMS 的 fork 参数）

### 方法 4：修改 APK（LSPatch 的路线）

直接把 hook 代码**打进 APK**：

```
原 APK
  ↓ 反编译
smali 代码
  ↓ 在 Application 里塞 hook 逻辑
重新打包 + 签名
  ↓
装上（不需要 root）
```

**优点**：不需要 root  
**缺点**：要重打包，签名变了，部分 App 会检测签名

## 🧬 Zygisk 的核心思想

**Zygote 是所有 App 的妈妈**：

```
init
 └── Zygote (加载了 framework.jar、所有系统类)
      ├── fork → com.tencent.mm   (微信)
      ├── fork → tv.danmaku.bili  (B站)
      ├── fork → com.android.settings
      └── fork → ... 每个 App 都是 Zygote 的儿子
```

**关键洞察**：所有 App 进程都是 Zygote fork 出来的。**如果你能控制 Zygote，你就能在每个 App 出生的那一刻往里塞代码**。

### Zygisk 做什么

**在 Zygote 进程启动时，把一段 .so 注入到 Zygote 里**。这样：

- Zygote 每次 fork 出新 App 进程，注入的 .so 也会跟着进新进程
- 在 App 进程里，这段 .so 可以做任何事——比如加载 LSPosed、加载 ZygiskNext

```
启动 Zygote
   ↓
Zygisk 把 libzygisk_next.so 注入到 Zygote
   ↓
Zygote fork 出微信进程
   ↓
微信进程里也有 libzygisk_next.so
   ↓
这个 .so 再去加载 LSPosed / ZygiskNext / 你的模块
```

## 🧬 Zygisk 模块的形态

Zygisk 模块本质是一个 `.so` 文件（动态链接库）。Zygisk 加载它之后会调它的**入口函数**：

```c
// 一个 Zygisk 模块的伪代码
void on_load() {
    // Zygisk 加载我时调用
}

void pre_app_specialize() {
    // App 进程刚 fork 出来，还没 exec 时调用
    // 我可以读 App 的包名，决定要不要在这个 App 里激活
}

void post_app_specialize() {
    // App 进程已经设置好，可以 hook 了
    // LSPosed 在这里加载模块
}
```

**ZygiskNext v1.3.0+ 就是个 Zygisk 模块**——它在 `pre_app_specialize` 里看包名，如果包名在排除列表里，就**抹掉**这个进程里所有 Zygisk 痕迹再"半卸载"自己。

## 🪝 ART Hook：LSPosed 干的事

### 核心：ArtMethod 替换

Android 的 Java/Kotlin 代码跑在 **ART**（Android Runtime）上。ART 里每个方法对应一个 **`ArtMethod` 结构体**（C++ 对象），里面有：

- `entry_point_from_jni_` → JNI 入口
- `entry_point_from_quick_compiled_code_` → 编译后的机器码入口

**LSPlant 干的事**：把 `ArtMethod` 的入口指针改成你自己的函数地址。下次这个方法被调用，CPU 跳到的是你的代码。

```kotlin
// 模块开发者的视角（你写的代码）
XposedHelpers.findAndHookMethod(
    "com.tencent.mm.ui.chatting.ChattingUI",
    lpparam.classLoader,
    "sendMessage",
    String::class.java,
    object : XC_MethodHook() {
        override fun beforeHookedMethod(param: MethodHookParam) {
            param.args[0] = "替换后的消息"
        }
    }
)
```

底层发生的就是 LSPlant 把 `sendMessage` 这个 ArtMethod 的入口改成了 LSPosed 的跳板函数。

## 🎯 为什么 LSP 模块"作用域"是优点

> 你可能疑惑："作用域限定在勾选的目标 App 里，岂不是很麻烦？"

恰恰相反，**作用域是 LSP 最大的优点**：

| 没有作用域（Xposed 老时代） | 有作用域（LSPosed 时代） |
|---|---|
| 模块对所有 App 生效 | 只对你勾选的 App 生效 |
| 一个 hook 写错，整机所有 App 都崩 | 崩了只崩那一个 App |
| 银行 App 检测到 hook 框架就闪退 | 银行 App 不在作用域，看不见你 |
| 性能损耗全局 | 性能损耗只在目标 App |

**勾选的代价 vs 全局污染的代价，前者几乎为零**。

## 🧪 亲手验证

```bash
adb shell

# 看 Zygote 进程
ps -ef | grep zygote
# 应该有 zygote64 和 zygote（32位和64位两个）

# 看一个 App 进程的父进程
ps -ef | grep com.tencent.mm
# 看 PPID 列，应该指向 zygote 的 PID

# 看进程的内存映射（要 root）
su -c "cat /proc/$(pidof com.tencent.mm)/maps | grep -i lsposed"
# 应该能看到 LSPosed 的 .so 在内存里

# 看进程的标签
su -c "cat /proc/$(pidof com.tencent.mm)/attr/current"
# 应该看到 u:r:untrusted_app:s0 之类
```

## 🎯 经典疑问

### Q1: 为啥 LSP 模块要重启目标 App 才生效？

因为 hook 是在**目标 App 启动时**（被 fork 出来时）注入的。已经在跑的 App 没法再注入——除非用 ptrace，但那是另一套机制。

### Q2: 我 hook 了微信，会影响 QQ 吗？

**不会**——只要你的模块在 LSPosed 里只勾选了微信作用域。QQ 进程里虽然也有 LSPosed 框架，但你的模块没被加载。

### Q3: Zygisk 注入是不是相当于"全局 hook"？

**对**——Zygisk 的 .so 会进**所有** App 进程。但**具体加载哪些模块**是按作用域控制的。

### Q4: ptrace 注入的优势是啥？

- 能 hook native（C/C++ 代码）
- 能 attach 已经在跑的进程（不需要重启目标）

**缺点**： ptrace 会被反调试检测，而且 SELinux 默认禁止跨标签 ptrace。
