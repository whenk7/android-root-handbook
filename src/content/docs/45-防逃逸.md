title: "防逃逸"
---

> 配置 App Profile 不当，App 能"绕开"你的限制——这叫**逃逸**。这篇讲怎么防。

---

## 🏃 什么是逃逸

**配置不当，App 能"绕开"你的限制**。

---

## 🎬 经典逃逸场景

### 场景 1：通过 ADB shell 提权

**配置失误**：

```
你给 ADB shell（UID 2000）允许 root（完整权限）
给某个 App 的 root profile 设 UID = 2000
```

**App 干的事**：

```
1. 第一次 su → KSU 拦截，把它切到 UID 2000
   （你以为安全了——它只是 shell）
   
2. 但 UID 2000 现在有 shell 权限
   它再跑 su
   
3. KSU 看到 UID 2000 在允许 root 的名单里
   → 给完整 root
   
4. App 拿到了完整 root！
```

**为啥能成**：
- 第一次 su 切到 UID 2000（受限）
- 第二次 su 时，**UID 2000 本身被允许拿 root**
- KSU 不知道这是"第二次 su"

---

### 场景 2：通过 setuid 二进制

**配置失误**：

```
你给一个 App 移除了所有 Capabilities
但保留了"执行任意命令"的能力
```

**App 干的事**：

```
1. App 跑：su -c "/system/bin/su"
2. /system/bin/su 是 setuid 二进制（root 所有）
3. 新进程拿到 root 完整权限
```

**为啥能成**：
- setuid 二进制的"提权"是 Linux 的机制
- KSU 的 Capabilities 限制不影响 setuid

---

### 场景 3：通过其他 setuid 工具

类似的：
- `sudo`（如果装了）
- `pkexec`
- 某些自带 setuid 的系统工具

---

## 🛡️ 防御：NO_NEW_PRIVS

### 是啥

**NO_NEW_PRIVS** 是 Linux 的进程标志：

> **这个进程之后不能通过任何方式提权**（不能 su、不能 sudo、不能跑 setuid 程序）。

一旦设置，**不可撤销**。

### 在 App Profile 里启用

KSU Manager → App Profile → 找到目标 App → 勾选 **"NO_NEW_PRIVS"**。

### 效果

```
App 拿到 su 之后：
- 想跑第二次 su → 失败
- 想跑 sudo → 失败
- 想跑 setuid 二进制 → 拿不到提权后的权限
```

---

## ⚠️ NO_NEW_PRIVS 不是万能

### 官方文档原话

> 但是，此标志**仅**阻止 KernelSU 为该进程提升权限，它仍然可以利用其他 Linux 机制来逃逸。
> 因此，请务必注意你的权限设置。

### 意思

NO_NEW_PRIVS 不能阻止：
- 利用内核漏洞
- 利用其他进程的 IPC 漏洞
- 利用 setuid 二进制的 bug

**Capabilities、SELinux、UID 限制才是主力**——NO_NEW_PRIVS 是兜底。

---

## 🛡️ 完整防逃逸清单

### 1. 启用 NO_NEW_PRIVS

默认所有 App 都开。

### 2. 谨慎给"非 root" App 配 root

**反例**：

```
给 ADB shell（UID 2000）配 root
给某个 App 的 root profile 也设 UID = 2000
→ 逃逸！
```

**正确**：
```
给 ADB shell 配 root → 用 UID 0
给 App 配 root → 用 UID 0，但限制 Capabilities
```

### 3. 最小化 Capabilities

不要保留"以为以后用得上"的权能——只留**确实需要**的。

### 4. 严格 SELinux

不要写 `allow * * * *`。

### 5. 清理 setuid 二进制

```
adb shell
su

# 看 /system 下哪些是 setuid
find /system -perm -4000 2>/dev/null

# 如果不是必须的，去掉 setuid 位
chmod u-s /path/to/binary
```

---

## 🎯 怎么验证你的配置有没有逃逸漏洞

### 测试 1：尝试二次 su

```bash
# 用目标 App 跑一次：
su -c "su -c id"

# 如果第二次 su 也成功了 → 有逃逸风险
# 如果第二次 su 失败 → NO_NEW_PRIVS 工作正常
```

### 测试 2：尝试 setuid

```bash
# 用目标 App 跑：
su -c "/system/bin/su -c id"

# 看输出
```

### 测试 3：跑 capabilities 测试

```bash
# 让目标 App 跑：
su -c "capsh --print"

# 看实际生效的 capabilities
```

## 🎯 推荐配置（终极防逃逸）

### 给一个 App"有限 root"的最严配置

```
App Profile for <不可信 App>:

[✓] 允许 Root

Root Profile:
  UID: 0
  GID: 0
  
  Groups:
    ✗ inet              ← 不能联网
    ✗ sdcard_rw         ← 不能写 SD 卡
    ✗ net_bt            ← 不能蓝牙
  
  Capabilities:
    ✓ CAP_DAC_OVERRIDE  ← 只能读写文件
    ✗ 其他全部移除
  
  SELinux Context:
    u:r:limited_app:s0   ← 自定义严格域
  
[✓] NO_NEW_PRIVS         ← 阻止二次提权

Non-Root Profile:
  卸载模块: 默认
```

**效果**：
- App 拿到 root 后能读写文件
- 不能联网
- 不能写 SD 卡
- 不能干其他任何事
- 不能二次提权
