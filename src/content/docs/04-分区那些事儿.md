---
title: "分区那些事儿（boot、init_boot、super、A/B 槽）"
---

> 手机存储不是一整块，是分了很多分区。这篇讲清楚**哪些分区是干啥的、哪些是 KSU 在碰的、什么是 A/B 槽**。

---

## 🧱 Android 都有哪些分区

```
/dev/block/by-name/
├── boot_a          ← 启动分区 A 槽（包含内核 + ramdisk）
├── boot_b          ← 启动分区 B 槽
├── init_boot_a     ← 新版 Android 的"启动 ramdisk"（A 槽）
├── init_boot_b
├── vbmeta_a        ← AVB 验证元数据
├── vbmeta_b
├── dtbo_a          ← 设备树 overlay
├── dtbo_b
├── vendor_boot_a   ← 厂商启动 ramdisk
├── vendor_boot_b
├── super           ← 动态分区容器（包含 system/vendor/product）
├── userdata        ← /data 分区的真身（**只有一份，不分槽**）
├── metadata        ← 加密密钥、OTA 状态
├── cache           ← 缓存（新版 Android 可能不要这个）
├── recovery        ← 恢复模式（A/B 机型通常没有，被 boot 取代）
├── lk_a            ← Little Kernel（bootloader 一层）
├── lk_b
└── ...
```

---

## 🥊 关键分区逐个讲

### boot.img（最重要的一个）

**包含**：
- **kernel**：Linux 内核二进制
- **ramdisk**：初始内存盘（早期 Android 在这里）

**谁在用**：
- 老 Android（≤12）：所有启动逻辑都在这
- 新 Android（13+）：ramdisk 被拆到 init_boot，boot 只剩 kernel 和通用 ramdisk

**KSU 的关系**：GKI 模式直接 patch 这里的 kernel，LKM 模式不动它。

---

### init_boot.img（Android 13+ 新增）

**包含**：第一阶段启动用的 ramdisk（厂商特定的初始化脚本）

**KSU 的关系**：**LKM 模式 patch 的就是它**——在 ramdisk 里塞 `ksuinit`，让 init 启动时先加载 kernelsu.ko。

**怎么判断你的手机用哪个**：
```bash
adb shell
ls /dev/block/by-name/ | grep -E "^boot|^init_boot"
```
- 只有 `boot_a`/`boot_b` → 老设计，KSU patch `boot`
- 有 `init_boot_a`/`init_boot_b` → 新设计，KSU patch `init_boot`

---

### vbmeta.img（AVB 验证元数据）

**干啥**：存储各个分区的哈希，用于 Android Verified Boot 验证。

**为啥重要**：
- 默认状态下，vbmeta 会校验 boot.img 签名
- 解锁 BL 后，vbmeta 校验关闭
- 刷第三方 recovery / 修改 boot 时常要禁用 vbmeta：
  ```
  fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
  ```

---

### super 分区（动态分区）

**背景**：传统分区大小**出厂固定**，OTA 升级塞不下就废。

**解法**：把 system/vendor/product/system_ext 等做成**逻辑分区**，放在一个大的 `super` 物理分区里：

```
super 分区（物理一整块）
├── system_a    (逻辑分区)
├── system_b
├── vendor_a
├── vendor_b
├── product_a
├── product_b
├── system_ext_a
└── ...
```

**好处**：每个逻辑分区大小可以**动态调整**（OTA 时按需分配）。

**对你的影响**：
- `mount | grep system` 看到的可能是 `/dev/block/dm-4`，不是 `/dev/block/sda30`
- 因为 dm 是 Linux 的 device mapper（逻辑卷管理），专门管 super 里的动态分区

---

### lk_a / lk_b（Little Kernel，bootloader 一层）

**`lk` = Little Kernel**，是很多 Android 手机用的 bootloader 的名字。

```
启动链：
PBL (Primary Boot Loader，固化在 ROM)
   ↓
XBL / SBL (厂商次级 loader)
   ↓
LK (Little Kernel) ← 这一层跑 fastboot！
   ↓
Linux kernel (boot.img)
```

**你在 fastboot 模式下交互的就是 lk**。

**警告**：**别动它**——刷错 lk = 彻底砖（连 fastboot 都进不去）。KSU 不碰 lk。

---

## 🔄 A/B 槽（无缝更新）

### 是什么

现代 Android（7.0+ 引入，11+ 强制要求）的**很多关键分区有两份**：

```
当前激活：A 槽
OTA 开始
   ↓
后台下载 OTA 包
   ↓
写到 B 槽（不影响你用 A 槽的系统）
   ↓
写完后系统提示重启
   ↓
重启时 bootloader 切到 B 槽启动
   ↓
你在用 B 槽的新系统了，A 槽变成"备份"
   ↓
下次 OTA：写到 A 槽
```

### 好处

- 更新过程**不打断用户**（后台下载、后台写入）
- 失败可回滚（bootloader 检测 B 槽启动失败会回退到 A）

### 不分槽的分区

- `userdata`：用户数据（总不能一份 App 装两遍）
- `metadata`：OTA 状态

### 怎么确认自己手机是不是 A/B

```bash
adb shell getprop ro.build.ab_update
# true = A/B
# false 或空 = 单槽（老手机）

# 看当前激活哪个槽
adb shell getprop ro.boot.slot_suffix
# _a 或 _b
```

### A/B 跟 root 的关系

这是刷 KSU 最容易翻车的地方：

- KSU 的 init_boot patch 是 patch **当前激活那个槽**
- OTA 更新后，新系统会被写到**另一个槽**——你 patch 的 init_boot 就丢了
- 正确做法：OTA 完成后，**在重启前**装 KSU 到"另一个槽"（Manager 里有"安装到未使用槽位"选项）

---

## 🧪 亲手看看你的手机

```bash
adb shell

# 1. 看是不是 A/B
getprop ro.build.ab_update

# 2. 看当前槽
getprop ro.boot.slot_suffix

# 3. 看分区列表
ls /dev/block/by-name/ | head -30

# 4. 看 super 里的逻辑分区
ls /dev/block/mapper/ 2>/dev/null

# 5. 看挂载
mount | grep -E " /system | /vendor | /data "

# 6. 看 /system 在哪个设备
mount | grep " /system "
# 输出示例：/dev/block/dm-4 on /system type erofs (ro,seclabel,relatime)
```

## 🎯 经典疑问

### Q1: 为啥我 OTA 之后 root 没了？

因为你 patch 的 init_boot 是**当前槽**的，OTA 写到了**另一槽**，重启后切到新槽，新槽的 init_boot 是原厂的。

**解法**：OTA 完成后，**先别重启**，在 KSU Manager 里点"安装到另一槽位"，再重启。

### Q2: 我能不能直接 fastboot flash 到指定槽？

可以：
```bash
fastboot flash init_boot_a rooted.img    # 刷到 A 槽
fastboot flash init_boot_b rooted.img    # 刷到 B 槽
fastboot --set-active=a                  # 切到 A 槽
```

### Q3: userdata 不分槽，那 OTA 出问题用户数据怎么办？

**这就是为啥 OTA 不会动 /data**。OTA 只改 system/vendor 等只读分区，用户数据完全不动。
