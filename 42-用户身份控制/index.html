    42 · 用户身份控制（UID / GID / Groups）¶

    App Profile 的第一层防护：控制 App 拿到 root 后的"身份证"。

    🆔 UID 是什么¶

    Linux 用 UID（User ID）标识用户：

    UID 0        = root（最高权限）
UID 1000     = system
UID 2000     = shell（adb shell）
UID 10000+   = 普通 App（每个 App 一个 UID）

    查看自己：

    adb shell id
# uid=2000(shell) gid=2000(shell) groups=...

    👥 GID 和补充组¶

    主 GID¶

    每个进程除了 UID，还有一个主 GID（通常跟 UID 一致）。

    补充组（Supplementary Groups）¶

    进程可以属于多个组。某些权限是通过组控制的：

    inet            → 可以创建网络 socket（联网）
sdcard_rw       → 可以读写 /sdcard
sdcard_r        → 只能读 /sdcard
net_bt          → 蓝牙
net_bt_admin    → 蓝牙管理
input           → 输入设备
log             → 读日志

    示例¶

    adb shell id 输出：

    uid=2000(shell) gid=2000(shell)
groups=2000(shell),1004(input),1007(log),1011(adb),
       1015(sdcard_rw),1028(sdcard_r),
       3001(net_bt_admin),3002(net_bt),3003(inet),...
context=u:r:shell:s0

    意思： - UID = 2000（shell） - GID = 2000 - 在 inet 组里（能联网） - 在 sdcard_rw 组里（能读写 SD 卡） - ...

    🛠️ Root Profile 改 UID / GID / Groups¶

    默认情况¶

    App 拿到 root 后： - UID 变成 0 - Groups 是 root 的 groups（一堆）

    等于啥都能干。

    Root Profile 改它¶

    让 App 拿到 su 后，实际身份是你指定的。

    🎬 三个经典例子¶

    例子 1：文件管理器，不让联网¶

    需求：你装了个文件管理器，给它 root 看系统文件。但你不想让它联网（防止它偷偷上传）。

    配置：

    Root Profile:
  UID: 0
  GID: 0
  Groups: 移除 inet

    效果：

    App 拿到 root 后：
- 能读写所有文件 ✓
- 不能创建网络 socket ✗
- 即使它有"网络权限"，su 之后也不能联网

    为啥有效： - Linux 创建网络 socket 需要进程在 inet 组里 - 你把 inet 移除了，socket() 系统调用直接失败

    例子 2：终端模拟器，只给 shell 级别¶

    需求：你给终端模拟器 root，但其实只想让它有 adb shell 级别的权限。

    配置：

    Root Profile:
  UID: 2000 (shell)
  GID: 2000
  Groups: shell 的标准组（inet, log, sdcard_rw, ...）

    效果：

    App 跑 su 之后：
- 拿到的是 UID 2000（shell）的权限
- 不是真 root（UID 0）
- 跑 id 看到的还是 shell

    为啥要这样： - 有些 App"要求 root"但其实只需要 shell 权限 - 给它真 root 太危险

    例子 3：完全锁定，啥也不给¶

    需求：完全隔离一个不可信 App。

    配置：

    Root Profile:
  UID: 1000
  GID: 1000
  Groups: （清空）

    效果：

    App 跑 su 之后：
- 权限还不如普通 shell
- 几乎啥都干不了

    这种用法少见，但演示了 Root Profile 的能力。

    ⚠️ 关键：内核强制¶

    KSU 官方文档原话¶

    与应用通过 su 主动切换用户或者组不同，Root Profile 是在内核中强制实施的，不依赖 root 应用的自觉行为，su 权限的授予完全取决于用户而非开发者。

    意思¶

    App 自己跑 su -c "id" 想切到 root： - KSU 内核直接拦截 - 把它切到你指定的 UID - App 没法绕

    🔍 验证¶

    看 App 拿到 root 后的真实 UID¶

    # 让一个 root App 跑 id
adb shell
su -c "su -c id <某 App 的 UID>"

# 或者让 App 自己跑 id 命令（看它输出）

    看进程的组¶

    # 看进程的所有权
adb shell su -c "cat /proc/<pid>/status | grep -E 'Uid|Gid|Groups'"

# 输出：
# Uid:  0    0    0    0
# Gid:  0    0    0    0
# Groups: 3001 3002 3003

    🆚 UID/GID/Groups vs Capabilities¶

    维度 UID/GID/Groups Capabilities
    控制什么 你是谁 你能干啥
    例子 UID 0 = root CAP_NET_ADMIN = 改网络
    粒度 粗（一组权限打包） 细（每个权能独立）
    历史 Unix 传统 Linux 2.2+

    它们配合用： - UID 决定身份 - Capabilities 决定在那个身份下能干什么

    🎯 经典疑问¶

    Q1: 我把 App 的 UID 改成 2000，它还能 root 吗？¶

    取决于你对"root"的定义： - UID 0 = 传统意义的 root - UID 2000 = shell（不是 root）

    UID 改成 2000 之后，App 拿到的是 shell 权限，不是 root。

    Q2: 我能改 App 本身的 UID 吗？¶

    不能——App 的 UID 是 Android 包管理器在装 App 时分配的，改不了。

    App Profile 改的是"App 拿到 su 后切换到的 UID"，不是 App 本身的 UID。

    Q3: Groups 里的 inet 是啥？¶

    inet 是 Linux 网络组，进程必须在 inet 组里才能创建网络 socket。

    移除 inet = 这个进程不能联网。
